### Faults found (NEW unless an existing blocker ID is cited)

- F1. **Edit Department always fails**: `patchDepartment` sends no `If-Match`, but `update_department` calls `require_version`, which makes the header mandatory → 400 `VALIDATION_ERROR` ("Some fields are invalid.") on every rename / description edit / Active↔Inactive toggle. Evidence `FE/features/doctors/infrastructure/data-sources/remote/doctors.api.ts:93-102`, `BE/catalog/views/hospital_department_detail.py:82-84`, `BE/catalog/services/departments.py:33-35`, `BE/core/concurrency.py:13-19`. Impact: departments can be created and deleted but never edited or deactivated. Fix (frontend): pass the department `version` (already in `Department.version`) and send `ifMatch(version)`; also invalidate on 409 `CONFLICT_VERSION`.
- F2. Department delete ConfirmModal says the department "cannot be deleted" (doctors assigned) yet still offers the red Delete button, which is a guaranteed 409. Evidence `DoctorsDepartmentsScreen.tsx:417-423,461-463`. Fix (frontend): hide/disable confirm when `assigned > 0`.
- F3. Departments empty-state "Add Department" is not wrapped in `Can perm="Doctors & Departments.add"` (header button is). A role with view-only access (e.g. the CORE-07 stopgap grant) gets a form that 403s. Evidence `DoctorsDepartmentsScreen.tsx:316-324` vs `194-198`. Fix (frontend).
- F4. Affected-booking times in ScheduleChangeModal are formatted in the **browser** time zone (`Intl.DateTimeFormat` without `timeZone`), not `hospitals.timezone` (D-09). Evidence `ScheduleChangeModal.tsx:78-86`. Impact: a non-IST browser shows wrong appointment times in the "these bookings will be cancelled" list. Fix (frontend): format with the hospital tz.
- F5. Contract drift: backend `AffectedBookingSerializer.token_label` is `allow_null=True`; frontend schema has `z.string()` (non-null), so a single affected booking without a token makes the whole dry-run response fail to parse ("The server sent an unexpected response") and the change can never be applied from the UI. Evidence `FE/.../doctors.response.ts:113-119`, `BE/scheduling/serializers/affected_booking_serializer.py:9`, `BE/appointments/models/appointment.py:97`. Low likelihood (both booking paths set a label) — fix (frontend): `.nullable()`.
- F6. Department `code` (and doctor `slug`, see Doctor Profile F8) is derived client-side by `slugify(name)`: a non-Latin name gives `''` (DRF rejects blank) and two names that slugify alike ("ENT" / "E.N.T.") collide (`duplicate("code")`); the user sees only "Some fields are invalid." and has no field to fix. Evidence `doctors.api.ts:41-48,85-91`, `BE/catalog/services/departments.py:15-24`. Fix (frontend): de-duplicate/suffix the code or expose it; (backend, optional): derive the code server-side.
- F7. Cross-cutting: every form here toasts `failure.message` only; DRF field errors (`fieldErrors`, e.g. `code: Already exists.`, `If-Match: required`, `ends_at: Must be after starts_at.`) are dropped, so all 400s read "Some fields are invalid.". Evidence `DeptModal.tsx:63-64`, `FE/core/error/toFailure.ts:100-109`, `BE/core/errors.py:9`. Fix (frontend): surface `fieldErrors` (first message) in toasts/fields.

### Faults found (NEW unless an existing blocker ID is cited)

- F1. **"Next 14 days" shows garbage times.** `resolved[].sessions[].starts_at/ends_at` are full ISO datetimes (`timeutil.combine_local(...).isoformat()` → `2026-10-07T09:00:00+05:30`), but `toExceptionSession` applies `hhmm()` = `slice(0,5)` → `"2026-"`, and `hhmmToLabel("2026-")` returns it unchanged → every bookable day reads "Morning 2026-–2026-". Evidence `FE/features/doctors/infrastructure/data-sources/remote/doctors.response.ts:20-22,173-180,223-227`, `UpcomingDays.tsx:37-39`, `BE/scheduling/services/doctor_schedule.py:118-131`, `BE/scheduling/services/materialise.py:116-124`. Fix (frontend): parse the datetime and render it in the hospital tz (or backend: emit local `HH:MM` like the other schedule fields).
- F2. **Add Doctor can strand a half-created doctor.** POST /doctors succeeds, then the weekly-sessions PUT runs inside `scheduleConfirm.run`, which swallows its own errors (toast only). On any PUT failure (bad hours → `ends_at` 400, overlap → 409 `SLOT_OVERLAP`, a role with `.add` but not `.edit` → 403) the page stays on `/doctors/new` with `doctor === null`; pressing Add Doctor again re-POSTs the same `slug` → 400 `slug: Already exists.` ("Some fields are invalid."). The doctor exists with no sessions. Evidence `DoctorDetailPageScreen.tsx:278-304`, `useScheduleConfirm.ts:44-57`, `BE/catalog/services/doctors.py:81-84`. Fix (frontend): after POST, `navigate` to `/doctors/{created.id}` (or keep the created id in state and PATCH/PUT on retry); validate hours before POST.
- F3. **Paise lost / fee inflated on save.** `toForm` puts `String(feeRupees)` (e.g. `"499.5"` for 49 950 paise) in the draft and `toInput` runs `digits()` over it, stripping the dot → `4995` → 499 500 paise; an unrelated save (photo, bio) multiplies such a fee ×10/×100. The follow-up fee keeps decimals until edited, then `digits()` strips them too. Evidence `DoctorDetailPageScreen.tsx:150-152,189-190,211-212,533,552`; `doctors.api.ts:142-146`. Seeds use whole rupees (`BE/devseed/data.py:157-161`), so it bites only fees set elsewhere. Fix (frontend): keep paise as integers end-to-end or allow one decimal separator and round.
- F4. Free consultations cannot be saved: the fee validator is `positiveAmount` (> 0) and `toForm` shows a ₹0 fee as empty, but the backend allows `consultation_fee_paise ≥ 0` (`ck_doctor_fee`). Any edit of a ₹0 doctor is blocked with "Consultation fee must be greater than zero.". Evidence `DoctorDetailPageScreen.tsx:137,189`; `BE/catalog/serializers/doctor_serializer.py:12`; `BE/catalog/models/doctor.py:62-64`. Fix (frontend) — or confirm with the client that ₹0 is not allowed and tighten the backend.
- F5. ExceptionModal with >1 window shows two contradictory notes: "Also kept unchanged: …" and "saving keeps only the one above", while the code keeps every extra window (`...exception.sessions.slice(1)`). Evidence `DateExceptionsPanel.tsx:112-121,170-178,198-202`. Fix (frontend): drop the second note.
- F6. Working Hours has no client check that "to" is after "from" (patterns and exceptions do); an inverted day reaches the backend → 400 `ends_at: Must be after starts_at.` shown as "Some fields are invalid." (and triggers F2 on a new doctor). Evidence `WeeklyHours.tsx:80-102`, `doctors.view.ts:238-246`, `BE/catalog/serializers/weekly_session_serializer.py:19-22`. Fix (frontend).
- F7. Time pickers offer only 15 fixed labels 8:00 am–8:00 pm (no 7 am, 10:30, 12:30, 9 pm…); only a time already stored is added back. Early/late OPDs cannot be configured from the web app. Evidence `FE/features/doctors/domain/calendar.ts:27-43`, `doctors.view.ts:284-291`. Fix (frontend): 15/30-minute steps over 24 h.
- F8. Doctor `slug = slugify(name)` with no field to edit: two doctors with the same name (e.g. two "Dr. Priya Sharma") or a non-Latin name cannot be added (400 `slug`). Evidence `doctors.api.ts:41-48,155-160`; `BE/catalog/services/doctors.py:74-84`. Fix (frontend: suffix on collision) or backend (derive a unique slug server-side).
- F9. "Today" for leave/exception defaults and the past/future split in ScheduleHistory is the browser's local date, not the hospital's (D-09); the backend splits on `local_today(hospital.timezone)`. Evidence `LeavePanel.tsx:76-77`, `DateExceptionsPanel.tsx:88`, `ScheduleHistory.tsx:30,46,57`, `BE doctor_schedule.py:139`. Low impact for IST browsers.
- F10. After the profile PATCH is applied, `saveWeek` is fire-and-forget (`void saveWeek(...)`), so `form.submitting` drops to false while the weekly-sessions dry run is still in flight; Save is clickable again and a second click can send a stale `If-Match` (PATCH before the detail refetch lands, or a second weekly PUT racing the first) → 409 `CONFLICT_VERSION` next to the success toast. Evidence `DoctorDetailPageScreen.tsx:309-311,382`; `useScheduleConfirm.ts:44-49`. Fix (frontend): await `saveWeek` inside `onApplied` / keep a busy flag.
- F11. Backend (low): a confirmed write re-computes the affected set at confirm time (`reconcile(..., confirm=True)`) and does not compare it with the previewed one, and the UI auto-confirms when the preview is empty — a booking made between preview and confirm is cancelled without ever being shown. Evidence `BE/scheduling/services/materialise.py:528-538`, `useScheduleConfirm.ts:50-53`. Fix (backend): accept the previewed `appointment_id`s (or a preview hash) and 409 when the set grew.
