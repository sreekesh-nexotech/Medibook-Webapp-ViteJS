# Ops Billing + Subscription Plans — UAT audit

> Appendix to [`docs/UAT_REPORT_2026-10-07.md`](../UAT_REPORT_2026-10-07.md). Static, code-level
> audit of web app commit `1ade3ae` against backend commit `b85a87b`; nothing here was run against a live
> backend. Paths under `src/` are in this repository (`medibook-webapp/`); paths under `medibook/` are in the
> Django backend repository; Flutter paths are under `lib/`. **NEW** marks a gap that is not yet logged in
> [`docs/BACKEND_BLOCKERS.md`](../BACKEND_BLOCKERS.md); other IDs (CORE-07, APPT-01, …) refer to that file.
> Status values: OK (wired to an existing endpoint with a matching contract), UI-only (local state only),
> Partial (wired, with a gap a tester will hit), Broken (a real fault), Blocked-backend (the backend lacks
> what the screen needs), Disabled (switched off on purpose, with an explanation), not built (the backend
> has it, the screen does not).

Platform role matrix used below (`core/seeds/v1.py:117-160`): **owner** all; **ops_manager** all except settings.edit/staff.*/compliance.del;
**finance** billing/plans/settlements/reports/analytics view+edit + hospitals.view (no plans.add, no plans.del, no hospitals.edit,
no dashboard.view); **support**/**compliance** no billing, no plans; **read_only** every `*.view`. `/platform/me` returns codes
without the `platform:` prefix (`accounts/views/platform_me.py:22`), matching `useOpsPermission` keys (`'billing.edit'`).

Backend permission per view (all verified in `medibook/subscriptions/views/platform_*.py`): GET invoices list/detail/pdf/export.csv,
payments list, dunning list, subscriptions list/detail = `billing.view`; POST mark-paid (Idempotency-Key required), reminders, void,
PATCH grace, POST payments/{id}/retry (Idempotency-Key, always 501), approve/reject, PATCH subscriptions/{id} = `billing.edit`;
**GET plan-change-requests = `billing.edit`** (`platform_plan_change_list.py:15`); GET plans, plans/{id}, subscribers = `plans.view`;
POST plans = `plans.add`; PATCH plans/{id}, POST archive = `plans.edit`; DELETE plans/{id} = `plans.del`.

### Faults found (NEW unless an existing blocker ID is cited)

- F1. Plan Changes tab/panel is offered to `billing.view` roles, but the list GET requires `billing.edit`. Evidence: `PlanChangesPanel.tsx:53`, `platform_plan_change_list.py:15`. Impact: read_only (and any view-only role) sees a 403 error panel. Fix: frontend. Hide the tab/panel unless `can('billing.edit')`. Backend alternative: relax GET to `billing.view`.
- F2. Bell "Queue payment reminder" on invoice rows is not permission-gated. Evidence: `OpsBillingScreen.tsx:535`. Impact: 403 toast for read_only. Fix: frontend, wrap in `CanOps perm="billing.edit"`.
- F3. Approving a plan change invalidates only `['ops-billing']`. Evidence: `useApprovePlanChangeMutation.ts:13`. Impact: ops-plans subscriber counts (`plansKeys.subscriberCount`) and ops-hospitals detail (`subscription.plan_id`) stay stale. Fix: frontend, also invalidate `plansKeys.all` and `hospitalsKeys.detail(hospitalId)`.
- F4. Approve discards `proration_invoice` and shows no preview of the amount before committing. Evidence: `billing.api.ts:159-163`. Impact: ops approve blind and cannot find the proration invoice from the toast. Fix: frontend shows/links the returned invoice; backend adds a preview (B6).
- F5. Payment/plan-change rows fetch the full hospital profile per hospital just to print a name. Evidence: `BillingHospitalName.tsx:12`. Impact: an extra heavy GET per distinct hospital on every page. Fix: backend adds `hospital_name` (B4).
- F6. Issued dates take the UTC calendar day. Evidence: `billingView.ts:64-66`. Impact: issue times 00:00–05:30 IST show one day early. Fix: frontend, format through the browser/hospital timezone.
- F7. Refresh does not refetch the KPI tiles. Evidence: `OpsBillingScreen.tsx:409-414`. Fix: frontend, refetch the four count queries too.
- F8. Reject dialog keeps the stale note after Cancel. Evidence: `PlanChangesPanel.tsx:214`. Fix: frontend, `setNote('')` in `onClose`.

### Needs API integration or rework

- R1. Subscriptions tab: absent. Needs GET /platform/billing/subscriptions (filters status, hospital_id, plan_id, billing_period; sort started_at/next_invoice_at), detail GET …/subscriptions/{id} (plan, status, trial_ends_at, current period, next_invoice_at, `read_only`, grace_days_override), and PATCH …/subscriptions/{id} + If-Match (ops plan/period change with proration, grace_days_override 0–90). All exist (`platform_subscription_list.py`, `platform_subscription_detail.py`); the frontend only reads the detail for plan name and override (`billing.response.ts:132-139`).
- R2. Dunning tab: absent. Needs GET /platform/billing/dunning?hospital_id&invoice_id&kind (timeline: reminder_queued, grace_started, grace_extended, read_only, reinstated, marked_paid, voided). The endpoint exists; today it is used only for one invoice's reminder kinds.
- R3. Hospital filter on Invoices and Payments: absent. Backend already accepts `hospital_id` (`billing_queries.py:34,51`); the entity even has `hospitalId` (`billing.entities.ts:156,170`).
- R4. MRR / Collected / Outstanding ₹ tiles: Blocked-backend. No `billing.view` endpoint returns sums. `GET /platform/dashboard` has `mrr_paise` and `invoices_outstanding_paise` but needs `dashboard.view`, which finance lacks (`analytics/views/platform_dashboard.py:12`). Needs B3.
- R5. Payments CSV beyond 100 rows: needs B7.

## Ops Payment Detail

How the screen gets its data: there is **no** `GET /platform/billing/payments/{id}` (`subscriptions/routes/platform.py:61-66`
have only the list and `/retry`). The screen calls the payments list and finds the row by id in the browser. With router state
`{invoiceId}` (set by the Payments tab, invoice detail and hospital card) it calls `GET /api/v1/platform/billing/payments?invoice_id=<id>&page=1&page_size=100&sort=-attempted_at`.
Without state (pasted/shared URL) it scans the **newest 100 payments platform-wide**, and an older payment shows "Payment not found".
Status history is synthesised in the browser from `status`/`attempted_at`/`captured_at`. No per-payment event history comes from the backend.
Retry: no button; backend retry is 501 by design.
