## 1. Scope, method and legend

**Scope.** Hospital console (`/:role/*`, 21 screens), operations console (`/ops/*`, 19 screens), the four sign-in pages and the emailed report-download page, the two shells (sidebar, topbar, bell, idle warning), the shared UI kit, and the patient app's booking and payment path. The full patient-app UAT is out of scope, as agreed.

**Method.** Thirteen web-app areas and the patient-app booking path were each audited element by element against the backend. "Element" means every tab, filter, search box, sort header, button, icon button, row action, link, status pill, KPI tile, chart, pager, empty, loading and error state, form field, upload control, modal and drawer. Each was checked for:

- the endpoint, method, fields, enums and pagination it sends and expects;
- the permission the backend enforces, against each seeded role;
- `Idempotency-Key` and `If-Match` where the backend requires them;
- which lists refresh after a change;
- copy that promises something the system does not do.

Every Critical fault in section 5, and the most serious findings of the other areas, were then re-checked by hand in both repositories. Those checks are listed in appendix 00.

**Element status**

| Status             | Meaning                                                                                                              |
| ------------------ | -------------------------------------------------------------------------------------------------------------------- |
| OK                 | Wired to an endpoint that exists, with a matching contract and permission.                                           |
| Partial            | Wired, but with a gap a tester will hit: wrong count, stale list, missing refresh, misleading copy, wrong role gate. |
| UI-only            | Local state only: client-side filtering or sorting, static copy, a control with no API behind it.                    |
| Broken             | A real fault: wrong field, missing header, dead handler, wrong navigation, wrong data.                               |
| Blocked by backend | The screen is right but the backend lacks the endpoint, field or permission.                                         |
| Not built          | The backend has the feature; the screen has no control for it.                                                       |
| Disabled           | Switched off on purpose, with an explanation on screen.                                                              |

**Step verdicts in section 4:** Pass, Partial (completes, with an issue a tester will notice), Fail (cannot complete as expected because of a fault), Blocked (cannot run until a backend or staging change lands).

**IDs.** `UAT-nn` are faults in this report (section 5). `BE-nn` are backend changes (section 7). ## 3. Creating online bookings for the web UAT

**The patient app cannot do it.** The Flutter app has no HTTP client on any of its six remote branches; its only client throws on every call, and every booking and payment screen runs on in-memory sample data (appendix 14). The integrated build behind the emulator booking of 1 October, described in the backend's `docs/FLUTTER_INTEGRATION_GAPS_ROUND_2.md`, was never pushed to this repository. Read from the code (not run): in its default demo mode, a correct sign-in never sets the signed-in state, so the app's route guard sends the user back to the sign-in page.

**Use the API instead.** Every request below already exists in `postman/medibook.postman_collection.json` in the backend repository. Use `curl -k` against staging while its certificate is self-signed.

| Step                          | Request                                                                                                                                     | Notes                                                                                                                                                                                                  |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 1. Sign in as a patient       | `POST /api/v1/patient/auth/login/password` `{"identifier":"+919808683257","password":"seed_password_123"}`                                  | Returns `access`, `refresh`. Send `Authorization: Bearer <access>` on every later call. OTP sign-in works only for numbers listed in `DEV_OTP_FIXED_CODES` and needs an `X-Device-Fingerprint` header. |
| 2. Find a hospital and doctor | `GET /api/v1/patient/hospitals?city=Kochi`, then `GET /api/v1/patient/hospitals/{id}/doctors?department_code=cardiology`                    | A hospital is listed only when it is active, visible and not read-only. Pick a doctor with `is_bookable_online: true`.                                                                                 |
| 3. **Capturing the payment (step 6) — decide this before UAT day.** On a fake-provider staging the normal checkout path cannot work: `POST /patient/payments/orders/{id}/verify` asks the fake gateway for a payment it never created and crashes with a 500 (`payments/services/online.py:222`, `integrations/razorpay/client.py:122-123`). Pick one of these:

1. **Signed webhook (works in fake mode).** Needs a non-empty `RAZORPAY_WEBHOOK_SECRET` on staging, shared with testers, and the webhooks worker running. Within the 5 minutes:

   ```sh
   BODY='{"event":"payment.captured","payload":{"payment":{"entity":{"id":"pay_uat_0001","order_id":"<payment_order.gateway_order_id>","amount":<payment_order.amount_paise>,"method":"upi"}}}}'
   SIG=$(printf '%s' "$BODY" | openssl dgst -sha256 -hmac "$RAZORPAY_WEBHOOK_SECRET" | sed 's/^.* //')
   curl -k -X POST "$BASE/webhooks/razorpay" -H 'Content-Type: application/json' \
        -H "X-Razorpay-Signature: $SIG" -H "X-Razorpay-Event-Id: evt_uat_0001" --data-binary "$BODY"
   ```

   Use a new payment id and event id for every booking. The amount must equal the order amount. The mount point is `/webhooks/razorpay`, not under `/api/v1`. The Postman webhook request has no body, and its note saying an empty secret works is wrong (BE-04).

2. **Razorpay test mode.** Test keys, `razorpay` in `PROVIDERS_LIVE`, auto-capture on in the Razorpay account (the backend never calls capture and treats "authorized" as paid), then a real test checkout and `verify`.
3. **Server shell.** Ops replays the webhook through `webhooks/services/receive` and `process` as the seeder does (`devseed/timeline.py:248-252`). Needs the owner database role.
4. **Re-seed.** `seed_demo --reset` creates about nine paid upcoming online bookings per live hospital. It wipes all data and only runs on a dev environment.

**Check that a hospital appears in the patient app** without the app: `GET /api/v1/patient/hospitals?q=<name>` needs no sign-in.
